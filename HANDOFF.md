# Handoff

State of RepTracker as of 2026-10-19. Written for whoever picks this up next — including
future-you after a few months away.

The [README](README.md) is the user-facing document: what it is, how to run it, how to deploy it,
what every environment variable does. **This file is the other half** — why things are the way they
are, what was verified and how, and what is deliberately missing.

## The four decisions everything else follows from

These were settled with the owner before any code was written. Reopening one is a real
architectural change, not a preference tweak.

1. **One deployable.** The API serves `/api/*` and falls through to the built React SPA. This is
   why there is no CORS config, no second host, no token juggling in the browser — just a
   same-site cookie. Splitting the frontend out later means adding all three back.
2. **A server-generated numeric code is the whole credential.** No email, no password, no reset.
3. **Online-only.** Every action is a request. This was chosen over a local-first PWA
   deliberately; see [Things deliberately not built](#things-deliberately-not-built).
4. **Routine templates plus ad-hoc sessions.** Both paths exist and share the same workout model.

## Layout

```
src/RepTracker.Api/
  Program.cs            startup, middleware order, connection-string resolution
  Config/               AppOptions (all tunables), RateLimits (all request-rate policy)
  Auth/                 LoginCode (Luhn), Tokens (hashing), SessionAuth (cookie -> user)
  Data/                 Entities, AppDb, ExerciseCatalog, Seeder, DemoData, Migrations/
  Endpoints/            one file per group + Dtos, Mapping, Validation, PreviousPerformance
  Stats/                Formulas (the training maths), StatsService (all dashboard numbers)

src/web/src/
  api/                  client (fetch + ApiError), types (mirrors the DTOs), hooks (TanStack Query)
  lib/                  units, time, totals, loginCode, useRestTimer, useElapsed, useMediaQuery
  components/           Sheet, ExercisePicker, Icons
  pages/                one per route, each with its own .css
  styles/               theme.css (UI tokens), viz.css (chart tokens)
```

`src/RepTracker.Api/wwwroot/` is generated by `npm run build` and is **not** in version control. A
fresh clone that runs only `dotnet run` serves no UI — build the web app first.

### API surface

```
/api/auth        POST register, POST login, POST logout, GET/PATCH/DELETE me
/api/exercises   GET, POST, PATCH :id, DELETE :id
/api/routines    GET, GET :id, POST, PUT :id, DELETE :id
/api/workouts    GET, GET active, POST, GET :id, PATCH :id, DELETE :id
                 POST/PUT/PATCH/DELETE .../exercises[/order|/:weId], POST .../exercises/:weId/swap
                 POST/PATCH/DELETE .../exercises/:weId/sets[/:setId]
/api/stats       GET overview, calendar, exercises, exercises/:id
/api/health      GET (unauthenticated)
```

Everything except `register`, `login` and `health` requires a session.

## Non-obvious things, and why

Each of these will look like a mistake until you know the reason.

**Login is a keyed hash, not a salted one.** `HMAC-SHA256(code, App__LoginPepper)`, indexed. A
per-user salt would make login a table scan, because there is no username to look up first. The
pepper lives in the environment, so a stolen database cannot be brute-forced without also stealing
the config. `Auth/Tokens.cs`.

**The Luhn check digit earns its keep in the browser, not the server.** The rate limiter is
middleware and runs before the handler, so a server-side rejection has already cost an attempt.
The identical check in `web/src/lib/loginCode.ts` is what stops typos from spending the login
budget; the server copy only saves a database lookup.

**Rate limiting runs after `UseAuthentication`, not before.** The global limiter partitions
signed-in traffic per account (240 a minute) and anonymous traffic per address (60), and it can only
tell the two apart once the session has been read. Until 2026-10-20 it ran first, so every signed-in
user was silently held to the anonymous budget. The price of the order is one indexed session lookup
for a request that is then refused; a request with no cookie costs nothing.

**Static files are served before `UseAuthentication`.** Otherwise every stylesheet and script
request runs the session handler and hits the database. Moving `UseStaticFiles` back below auth in
`Program.cs` silently reintroduces that. The ordering is load-bearing.

**Weight is stored in kilograms everywhere** — database, API, and every statistic. kg/lb is a
display conversion in `lib/units.ts`. Switching units never rewrites history. The user's weight
step (`User.WeightStepKg`, Settings) follows the same rule, at three decimal places so a 5 lb step
round-trips as 5; null means the per-unit default in `lib/units.ts`.

**One active workout per user is enforced by a partial unique index**
(`IX_Workouts_OneActivePerUser`), not just by the handler's check. A double-tapped "Start" races
past the check; `WorkoutEndpoints.Start` catches the resulting `DbUpdateException` and returns
409 with the workout that won, which the client treats as "resume".

**Live totals are computed client-side** in `lib/totals.ts`, mirroring `Stats/Formulas.cs`. Set
edits are written straight into the query cache to stop the row flickering under your thumb, which
leaves the server's totals a step behind. **If you change a volume rule, change it in both files.**

**The live workout shows one exercise at a time.** The big steppers (`LogSetCard`) edit the next
unticked set, or a new one once the plan runs out, and the tick writes and completes it in one
request. Which exercise is on screen lives in `sessionStorage` (`rt.current-exercise`), like the
rest timer, so a reload lands back on it. On a phone the tab bar is hidden on `/workout`
(`.app.focus-mode`); Back is the way out.

**A workout exercise opens on last time's sets, not the routine's targets.** Starting a routine
or adding an exercise copies the sets from the most recent finished workout containing that
exercise (any routine, warm-ups included, unticked), via `CarryOver` in `WorkoutEndpoints`. An
exercise never done before starts clean: the routine's set count as empty rows, or no rows when
added ad hoc. Routine target weight and reps are deliberately ignored here (owner decision,
2026-10-19); they remain the written plan shown on the Train card. On such a first attempt, logging
a set copies its values into the still-empty rows after it (`logged` in `ExerciseFocus`), so the
next set is prefilled and a blank row can never be ticked as an empty set.

**Swapping an exercise mid-workout never rewrites sets already done** (2026-10-20). With nothing
ticked yet, `POST .../exercises/:weId/swap` replaces the exercise where it stands; with sets done,
those stay with the original - rewriting them would falsify its history and PRs - and the substitute
is inserted after it with the remaining set count. Either way it opens on its own last time's sets.
The picker leads with substitutes from `lib/similar.ts`, which ranks by movement family (a
pulldown is a vertical pull, so pull-ups and chin-ups come before rows, and deadlifts never come up)
before muscle group, since "Back" alone would offer a deadlift for a lat pulldown.

**The editors avoid effect-based state sync.** `SetRow` skips its re-sync while one of its own
inputs holds focus; `RoutineEditor` and `LogSetCard` seed during render against the id of what they
are editing. All guard the same bug: a refetch landing mid-edit replacing a value under the cursor. This is routine on a
phone, where tabbing away and back triggers a refetch.

**Never call `queryClient.clear()` to sign out.** It removes the query objects that mounted
observers are attached to, and those observers keep reading the removed entry — so the `useMe()` in
`App`, which gates the whole app, never sees the change and the user is left on a shell of empty
pages until they reload. `signOut()` in `api/hooks.ts` writes `me` first and removes only the other
keys. A 401 from any query or mutation routes through the same helper (`main.tsx`), so an expired
or revoked session drops to the login screen the same way an explicit sign-out does.

**Personal records are reconstructed by replaying history**, not stored in a records table. Editing
or deleting a set therefore corrects the New PR badges instead of leaving a phantom behind.
`StatsService.BuildRecordHistory`.

**Signed-out visitors land on a landing page** (`pages/Landing.tsx`, owner decision 2026-10-20). Its
buttons open the existing sign-in card in either mode, with a way back. It is lazy-loaded, so
signed-in users never download it.

**The whole app shares the landing page's look** (2026-10-20): its charcoal/chalk palette in
`theme.css`, Big Shoulders for headings and Figtree for everything else. Both fonts are bundled from
`@fontsource-variable` packages (imported in `main.tsx`) rather than fetched from Google, so the app
still makes no third-party requests. **Big Shoulders has no tabular figures** - a 1 is half the
width of a 0 - so it is only for headings and for numbers that never change on screen (stats tiles,
history dates, a finished workout's totals). Clocks, timers and steppers stay in Figtree with
`tabular-nums`, or they shuffle sideways as they tick. Small labels are sentence case, not tracked
capitals. When the surfaces changed, the chart colours were re-run through the validator: the dark
ramp's darkest step was re-stepped (it fell under 2:1 on the lighter card), everything else passed.
`--text-faint` now clears 4.5:1 on cards in both themes. Its features hang off a barbell, loaded in competition plate colours with the
heaviest first, so the order of the cards is the order of importance. The set-logging and
rest-timer cards are working demos with their own state. They must never reuse `useRestTimer`,
which would write into the real timer's `sessionStorage` slot.

**Workouts import from a CSV export, one row per set** (Settings, `POST /api/import/workouts`,
2026-10-20). The format is the owner's own export: `Date,Exercise,Set #,Reps,Weight,Duration,Distance,
Resistance,Notes`, dates like `17-Aug-2023`. Every set on one date is one workout. The file goes up as
the raw `text/csv` body, so that endpoint alone can raise the 64 KB body cap to 2 MB, per request.
Without `?commit=true` it only previews; with it, it writes everything in one `SaveChanges` - and
nothing at all if any row has an error. Parsing is pure and separate from the endpoint
(`Import/Csv.cs`, `Import/WorkoutCsv.cs`, `Import/ExerciseGuess.cs`), which makes it the easiest
thing in the app to put tests around; the owner's real export (7,150 rows, 563 workouts) imported
cleanly in about a second. Things that will look odd:
- *Late-December dates are moved back a year when the file says so.* The exporting app formatted
  dates with the week-numbering year, so 30 December 2024 came out as 30-Dec-2025. A 29-31 December
  date is corrected only when it is out of order with its neighbours and a year earlier puts it back in
  sequence (`CorrectWeekYears`); every correction is listed in the preview.
- *A set with 0 reps and no duration is skipped* as a placeholder never done (296 in the owner's
  file). Duration `0` means "not timed". Set #, Distance and Resistance are read past.
- *Workouts are named from what was trained* - Push, Pull, Legs, Upper body or Full body, by the
  patterns of their sets - because the export has no workout name.
- *New exercises get a guessed muscle group, pattern and equipment* from words in the name
  (`ExerciseGuess`: "Bayesian Curls" is Biceps/pull). There is no screen for editing a custom
  exercise's muscle group, so the preview lists every guess, grouped, before anything is written.
- *Exercise names match loosely* - case, spaces, hyphens and a plural s are ignored, and a few
  unambiguous shorthands (`squat`, `ohp`, `rdl`; not `row`) map to catalogue lifts. Every match under a
  different name is listed in the preview.
- *Re-importing is harmless*: a workout starting at the same instant as an existing one is skipped -
  matched on the start alone, so it holds even if the naming rules change. Imports start at noon.
- *Imported workouts have no duration* (the export carries none), so the detail page shows a dash
  for time and they add nothing to time-trained totals.
- *Separator and decimals are sniffed* (a European Excel writes `;` and `102,5`), and dates convert in
  the browser's named zone (`timeZone=Europe/Copenhagen`), not its current offset.
- The per-account caps (workouts, exercises per workout, sets per exercise, custom exercises) apply.

**Stats has two tabs: Overview (`/stats`) and Exercises (`/stats/exercises`).** Exercises lists every
exercise with a completed working set in the last three years. Each row opens the per-exercise page
at `/stats/exercises/:id`. It replaced the overview's Recent records and Worth a look cards (owner
decision, 2026-10-20). Their signals became badges on the rows: **New PR** when the best estimated
1RM beat an *earlier* best within 30 days, so a first session never counts; **Stalled** when the best
is 6+ weeks old despite 3+ sessions since, and the exercise was done in the last 21 days. The
"skipped in a routine" signal was dropped; each row's Last done column covers it. The list's
search, filter and sort live in the URL query, so Back from an exercise returns to the same view.
On the demo account most lifts show New PR, because `DemoData` progresses steadily. That's
expected.

**Estimated 1RM is discarded above 12 reps.** Past there Epley stops tracking strength. Those sets
still count as volume. `Formulas.EstimatedOneRepMax`.

**Bodyweight movements use `user.BodyWeightKg` plus any added load.** With bodyweight unset,
pull-ups record as zero volume and produce no strength estimate. The Settings copy says so.

**The rest timer counts to a wall-clock instant**, not by decrementing a tick — phones throttle
timers in backgrounded tabs, and the screen is off for most of a three-minute rest. The target is
also written to `sessionStorage` so a reload does not lose it. `lib/useRestTimer.ts`. Its `add()`
takes negative seconds (the dock's -15s) but never moves the end into the past.

**The app makes no sound and no vibration.** Owner decision (2026-10-19): headphones are usually
in, and a tone cut into whatever was playing. A finished rest shows "Go" in the dock and nothing
else. Do not add an audio or `navigator.vibrate` cue back without asking.

**`Sheet` reads `onClose` through a ref, and focuses itself once per opening.** Every caller passes
`onClose` inline, and the rest timer re-renders the workout page four times a second; with
`onClose` as an effect dependency the effect re-ran each time and its `focus()` pulled the cursor
out of any field in the sheet. It also skips that `focus()` when a field inside already has focus,
or `autoFocus` (the exercise picker's search) never sticks.

**Stats bucket weeks in the browser's timezone.** The client sends `offsetMinutes`; the server
clamps it to ±840. Weeks start Monday. The dashboard's periods read as months (1M/3M/6M/12M) but
are whole weeks underneath — 4, 13, 26, 52 — because the window always starts on a Monday.

**The volume chart switches from weekly to daily bars on short periods** (owner decision,
2026-10-20). Up to 13 weeks (`DailyVolumeMaxWeeks` in `StatsService`) it is one bar per day with a
7-day average; above that, one bar per week with a 4-week average. The server picks, and says which
in `volume.bucket`. A daily series ends today, not on Sunday, so 1M is 22-28 bars depending on the
weekday. The 7-day line sits well under the bars on purpose: it averages over rest days too.

**The consistency calendar follows the selected period and is binary.** One column per week of the
period, each day trained or not; set counts deliberately do not shade it (owner decision). The
server builds its days from *finished workouts* over the same Monday-start window as the overview
(`LocalMidnightUtc`), not from sets — otherwise a workout finished without a ticked working set is
counted in the Workouts tile but missing from the calendar.

**The hard-sets band is 4-8 sets a week**, an owner choice rather than the 10-20 of the training
literature, so the copy under the chart states the range without claiming research behind it. The
bar scale is fixed at 1.5x the band's top so the band sits in the same place on every row.

**Npgsql only binds `timestamptz` parameters at zero offset.** Any `DateTimeOffset` reaching a
query needs `.ToUniversalTime()`. This threw at runtime twice during the build — once in the stats
window, once on the history cursor. Both are fixed and commented; the trap is still live for new
queries.

**Stats are desktop-only.** An owner decision (2026-10-19): on a phone the app is for logging the
workout in front of you. Below 900px the Stats tab is not rendered and `/stats*` redirects to `/`;
workout detail renders exercise names as plain text rather than as links into stats. The 900px
value lives twice — `useIsDesktop` in `lib/useMediaQuery.ts` and the nav breakpoint in
`styles/theme.css` — so change both together. The route guard sits *above* `Lazy` on purpose, so a
phone never downloads the Recharts chunk.

**Recharts animation is off everywhere.** It replays on every filter change and every resize,
which reads as a glitch on a data page.

**Chart colours are validated, not chosen.** The categorical pair and the sequential ramp in
`styles/viz.css` were run through a contrast and colour-vision validator against this app's own
light *and* dark surfaces. If you change them, re-validate rather than eyeballing — three of the
checks are not judgeable by eye. The binary calendar uses only the ramp's strongest step
(`--heat-4`), for the most contrast against an empty day in both themes.

## What was verified, and how

There is **no automated test suite**. Everything below was checked by hand against a running
system. That is the central gap; see the next section.

**Against the production container** (built image, real Postgres):

| Check | Result |
|---|---|
| Login rate limit | 8 × 401, then 429 |
| Register rate limit | 429 with `Retry-After: 3600` |
| `MaxAccounts` ceiling | 403 |
| 200 KB body vs the 64 KB cap | 413 |
| All five API groups, unauthenticated | 401 |
| SPA deep links (`/stats`, `/history/:id`) | 200 |
| `/assets/nope.js` | 404 — the fallback correctly excludes file-shaped paths |
| Hashed assets / SPA shell | `immutable` / `no-cache` |
| Session cookie | `HttpOnly`, `SameSite=Lax`, `Secure` under TLS |
| Wrong pepper | every existing code rejected, exactly as documented |

**Against the browser** (Playwright, phone and desktop, light and dark): register → login → start
from a routine → tick sets → rest timer fires → add exercise → finish; history, workout detail,
routine editor, dashboard, per-exercise stats. No console errors.

Three bugs were found by *looking* at the running app that reading the code would not have caught:
stale header totals, chart bars touching at phone width, and the mid-typing overwrite. Worth
repeating the technique on the next change.

The October round of changes (focus workout screen, carry-over, rest controls, stats periods) was
verified the same way, change by change, with throwaway Playwright scripts against the dev servers.
That is how four more surfaced: the sheet stealing focus from the notes field mid-rest, the
calendar disagreeing with the Workouts tile, the active-workout query resolving to `undefined` when
none is open, and the Balance card butting against the grid above it.

## Known gaps and rough edges

Ordered by what to fix first.

1. **No tests.** Highest-value next work. The obvious targets: `Formulas` and `StatsService` (pure
   maths over fabricated set data), then endpoint tests over the auth and ownership boundaries.
   `DemoData` already builds a realistic history and is a reasonable fixture source.
2. **Rate limit state is in-process.** Correct for one instance, wrong the moment a second one
   exists — each replica would grant a full budget. Two instances needs a shared store.
3. **`MaxAccounts` has a benign race.** Concurrent registrations can both pass the count check. It
   is an approximate ceiling, not an exact one.
4. **`App__TrustProxyHeaders` clears the known-proxy list.** Necessary because platform proxy IPs
   are not known ahead of time, and safe *only* while the container is unreachable except through
   that proxy. Expose the port directly with this on and anyone can forge `X-Forwarded-For` and
   hand themselves a fresh rate-limit budget.
5. **Static files are outside the rate limiter** (it returns `NoLimiter` for non-`/api` paths).
   Cheap and cacheable, so this leans on the platform's own limits.
6. **The history list stops at 20, on purpose** (owner decision, 2026-10-20). Older workouts are
   reached through the month calendar above it, which asks `GET /api/workouts` for one month with
   `after` and `before` (local midnights) and `limit=100`. The month lives in the URL
   (`?month=2026-08`), so Back from a workout returns to it. Hover or keyboard focus on a day shows
   a quick look; touch has no hover, so a tap opens the workout, and a day with two workouts lists
   both under the grid instead. Nothing calls the keyset cursor for a second page.
7. **Workout exercises cannot be reordered from the UI.** `PUT .../exercises/order` exists and
   works; nothing calls it.
8. **The catalogue is English-only and has no i18n**, as is all UI copy.
9. **Bundle is ~109 KB gzip initial**, with Recharts (~107 KB) split into the stats routes — which
   phones never load, since stats are desktop-only.

## Things deliberately not built

Not oversights. Each was considered and declined for a stated reason.

- **Offline / PWA.** Explicitly chosen against in favour of "online-only, simplest". The rest timer
  and elapsed clock are still wall-clock based, so they behave correctly across a locked screen —
  that is timer correctness, not offline support. Revisiting this is the single biggest UX upgrade
  available, and the single biggest piece of work.
- **Account recovery.** Follows from the auth model. Both the sign-up flow and Settings say plainly
  that a lost code is a lost account.
- **A stored records table.** Replaying history is cheaper to keep correct at this scale.
- **Social features, sharing, media.** Out of scope for a personal tracker.

## Working on it

```bash
docker compose up -d db                        # Postgres on :5432
cd src/RepTracker.Api && dotnet run             # API on :5199
cd src/web && npm run dev                       # Vite on :5173, proxies /api
```

`dotnet run -- seed-demo` mints an account with ~20 weeks of training and prints its login code —
the fastest way to get a populated dashboard. It refuses to run outside Development because it
mints a whole account with backdated history. (The CSV import also backdates workouts, but only into
the signed-in user's own account, which is their history to write.) It also plants one deliberately
stalled lift (Overhead Press) so the stalling detector has something to find.

Before committing:

```bash
dotnet build                                    # expect 0 warnings
cd src/web && npx tsc --noEmit -p tsconfig.app.json && npx oxlint src
```

**Schema changes** need `dotnet ef migrations add <Name> -o Data/Migrations`. Migrations apply
automatically at startup, so a deploy needs no separate step — which also means a bad migration
takes the app down with it. A running `dotnet run` locks the build output on Windows; stop it before
adding a migration or building.

**Browser-test scripts and the login limit.** Login allows 8 attempts per 15 minutes per client, and
a script that signs in on every run spends that fast. Sign in once with a direct request to `:5199`
and hand the `rt_session` cookie to the browser context instead.
