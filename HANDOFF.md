# Handoff

Why RepTracker is built the way it is, the traps in it, and what is deliberately missing. What it
is, and how to run, deploy and configure it, is in the [README](README.md).

Points marked **owner decision** were settled with the owner. Ask before reversing them.

---

## The decisions everything follows from

1. **One deployable.** The API serves `/api/*` and falls through to the built SPA. So there is no
   CORS, no second host and no tokens in the browser, just a same-site cookie.
2. **A server-generated 20-digit code is the whole credential.** No email, no password, no reset.
3. **A workout in progress lives on the phone; only Finish sends it** (owner decision). Over phone
   data a request per tick felt unresponsive. Everything else (history, stats, routines, settings)
   is fetched live.
4. **Routine templates and ad-hoc sessions** share one workout model.

## Layout

```
src/RepTracker.Api/
  Program.cs            startup, middleware order (load-bearing, see below)
  Config/               AppOptions (all tunables), RateLimits
  Auth/                 LoginCode (Luhn), Tokens (hashing), SessionAuth (cookie -> user)
  Data/                 Entities, AppDb, ExerciseCatalog, Seeder, DemoData, Migrations/
  Endpoints/            one file per group, plus Dtos, Mapping, Validation, ExerciseMerges
  Import/               CSV parsing and export, pure and separate from the endpoints
  Stats/                Formulas (training maths), StatsService, Outliers

src/web/src/
  api/                  client, types (mirror the DTOs), hooks (TanStack Query)
  lib/                  liveWorkout (the workout in progress), setFields, totals, units, time, ...
  components/           Sheet, ExercisePicker, MergeExercises, ExerciseOutliers, SessionEditor, ...
  pages/                one per route, each with its own .css
  styles/               theme.css (UI tokens), viz.css (chart tokens)
```

`src/RepTracker.Api/wwwroot/` is generated by `npm run build` and not in version control. A fresh
clone that only runs `dotnet run` serves no UI.

### API

```
/api/auth        POST register, login, logout; GET/PATCH/DELETE me
/api/exercises   GET, POST, PATCH :id, DELETE :id, POST merge (?commit=true writes)
/api/routines    GET, GET :id, POST, PUT :id, DELETE :id
/api/workouts    GET (history), GET previous, POST (save a finished workout), GET :id,
                 DELETE :id, PATCH :id/exercises/:weId/sets (correct a saved workout)
/api/import      POST workouts (raw text/csv; ?commit=true writes)
/api/export      GET workouts (CSV)
/api/stats       GET overview, calendar, exercises, exercises/:id, exercises/:id/outliers,
                 exercises/:id/sessions/:workoutId
/api/health      GET
```

Everything except `register`, `login` and `health` needs a session. An unknown `/api/*` path is a
404, not the SPA shell.

## Server traps

- **Middleware order in `Program.cs` is load-bearing.** Static files are served *before*
  authentication, or every asset request costs a session lookup. The rate limiter runs *after*
  authentication, because it limits signed-in traffic per account (240/min) and anonymous traffic
  per IP (60/min), and can only tell them apart once the session is read.
- **Login is a keyed hash, not a salted one**: `HMAC-SHA256(code, App__LoginPepper)`, indexed. A
  salt would make login a table scan, since there is no username to look up first.
- **The Luhn check digit matters in the browser** (`lib/loginCode.ts`). The rate limiter runs
  before the handler, so a typo rejected by the server has already spent a login attempt.
- **Npgsql only binds `timestamptz` at zero offset.** Any `DateTimeOffset` in a query needs
  `.ToUniversalTime()`.
- **New child rows with preset ids go through the context.** Added only to the collection of a
  parent EF already tracks, EF takes them for existing rows and the save fails with
  `DbUpdateConcurrencyException`. This broke every routine edit until it was found.
- **Migrations run at startup**, so a bad migration takes the app down with it.

## The workout in progress

- **It lives in `localStorage`** (`rt.workout`), tagged with the user's id. Every edit is a pure
  function in `lib/liveWorkout.ts`, so a tap never waits on the network.
- **Start makes one request**, `GET /api/workouts/previous`: last time's sets for every exercise from
  the last 400 days, so adding or swapping one mid-workout needs no further request. With no signal
  it starts without them.
- **Finish sends it whole** (`POST /api/workouts`, completed sets only). The phone mints the id and
  the server answers a repeat save with the stored workout, so retrying is safe. `useSaveWorkout` runs
  with `networkMode: 'always'` so no signal shows an error instead of "Saving..." forever. The local
  copy is cleared only once the server has it.
- **It exists on one device only.** Cleared browser data or a private tab loses it before it is
  saved (owner decision).
- **Two pairs of things must change together:** the per-workout caps `MAX_EXERCISES`/`MAX_SETS`
  mirror `AppOptions.Limits`, and `lib/totals.ts` mirrors `Stats/Formulas.cs`.
- **`ActiveWorkout` sets a `leaving` ref before clearing on Finish.** The saved workout's page is
  lazy-loaded, and without it the "no workout, go home" effect fires first and lands on Train.
- **An exercise opens on last time's sets, not the routine's targets** (owner decision). Never done
  before, it gets the routine's set count as empty rows, and the first logged set is copied into
  them.
- **Swapping never rewrites sets already done.** With some done, the substitute goes in after the
  original, so the original's history and records stay true.
- **The rest timer counts to a wall-clock instant**, since phones throttle timers with the screen
  off. It and the current exercise survive a reload via `sessionStorage`.
- **No sound and no vibration** (owner decision: headphones are usually in).
- **Editors never let an update overwrite a field being typed in.** `SetRow` skips re-syncing while
  focused; `LogSetCard` and `RoutineEditor` seed during render against the id being edited.
- **`Sheet` reads `onClose` through a ref and focuses once per opening.** Otherwise the rest timer's
  re-renders, four a second, keep pulling the cursor out of its fields.

## Data rules

- **Kilograms everywhere**; kg/lb is display only (`lib/units.ts`). `User.WeightStepKg` has three
  decimals so a 5 lb step round-trips as 5.
- **Records are replayed from history**, not stored, so editing or deleting a set corrects them.
- **Estimated 1RM (Epley) ignores sets above 12 reps.** They still count as volume.
- **Bodyweight moves use `BodyWeightKg` plus added load.** With bodyweight unset they log zero volume.
- **There are no warm-up sets** (owner decision). Every completed set counts.
- **Weeks start Monday in the browser's timezone.** The client sends `offsetMinutes`. Stats periods
  read as months but are whole weeks underneath (4, 13, 26, 52).

## Import and export

The CSV format is the owner's own export, one row per set:
`Date,Exercise,Set #,Reps,Weight,Duration,Distance,Resistance,Notes`. Every set on a date is one
workout. Without `?commit=true` the import only previews; with it, it writes all or nothing. That
endpoint alone raises the 64 KB body cap, to 2 MB. Things that look odd:

- A 29-31 December date out of order with its neighbours moves back a year. The source app wrote
  week-numbering years.
- Sets with 0 reps and no duration are skipped as placeholders.
- Workouts are named by what was trained (Push, Pull, Legs, ...), as the export has no names.
- New exercises get a guessed muscle group, pattern and equipment (`ExerciseGuess`). There is no
  screen to edit those, so the preview lists every guess.
- Names match loosely (case, spacing, hyphens, plural s, a few shorthands like `ohp`).
- A workout starting within a minute of an existing one is a duplicate, so re-importing is harmless.
- Imported workouts have no duration. Untimed dates start at noon.
- `;` separators and `102,5` decimals are detected.

Export writes the same format plus a time in the Date cell, which the import reads. Noon is written
as the date alone, so an import exports back unchanged.

## Exercise merging

Stats > Exercises > Merge exercises (owner decision). `POST /api/exercises/merge` previews unless
`?commit=true`. Every set moves to the kept exercise, and routines switch over. A workout with both
gets their sets combined under the kept one, in the order done. A routine with both drops the other.

- **A built-in exercise is hidden for that account, not deleted.** The catalogue is shared. A
  user's own exercise is deleted.
- **Merges are remembered** (`ExerciseMerge`). Workout save, routine save and import redirect old
  ids and names through them, since a phone or another tab can hold an id from before the merge.
  Merging the kept exercise away later re-points the older rows, so a redirect is always one hop.
- Different exercise types (weight vs time, say) cannot merge.

## Logging mistakes and corrections

Each exercise's stats page lists **possible logging mistakes** (`Stats/Outliers.cs`): sessions whose
top set is more than 1.75x off from *every* one of the 3 sessions before and the 3 after.
- **The rule is tuned on the owner's real data.** Comparing with the immediate neighbours alone
  flagged 172 of 2,840 sessions, mostly a heavy and a light variant alternating under one name. This
  rule flags 39, the typos among them, plus a few real ones only the owner can judge.
- **There is no "this is right" button** (owner decision), so a correct flagged session stays listed.
- The first and latest sessions are never flagged; there is nothing on one side to judge them by.
- **Adjust** sets weight and reps to the average of the matching sets either side (owner decision).
  **Remove** deletes sets. Only that exercise's sets in that workout change.

**Clicking any point on the 1RM or volume chart** opens `SessionEditor` for that session: editable
values, a remove toggle per set, and "Fill from the sessions around it". Recharts reports a click it
has not tracked as `activeTooltipIndex: null`, and `Number(null)` is 0, so `pickHandler` must ignore
null or it opens the first session.

## Stats and look

- **Stats are desktop-only** (owner decision). Below 900px the tab is hidden and `/stats*` redirects
  home. The 900px lives in both `lib/useMediaQuery.ts` and `styles/theme.css`. The route guard sits
  above `Lazy` so phones never download Recharts.
- **Exercises tab badges:** New PR when the best estimated 1RM beat an *earlier* best within 30 days;
  Stalled when the best is 6+ weeks old despite 3+ sessions since, and the lift was done in the
  last 21 days.
- **The volume chart is daily up to 13 weeks, weekly above**; the server decides. The consistency
  calendar is binary and built from finished workouts. The hard-sets band is 4-8 a week (owner
  decision, not the literature's 10-20).
- **Recharts animation is off everywhere**; it replays on every filter change.
- **Chart colours are validated, not chosen** (`styles/viz.css`) for contrast and colour-blindness in
  both themes. Re-run a validator after changing them; eyeballing is not enough.
- **Big Shoulders has no tabular figures**, so it is only for headings and numbers that never change.
  Clocks, timers and steppers use Figtree with `tabular-nums`. Fonts are bundled, not fetched.
- **Never call `queryClient.clear()` to sign out.** Mounted observers keep reading the removed
  entries and the app never notices. `signOut()` in `api/hooks.ts` is the way, and every 401 goes
  through it.
- The landing page's demo cards must not reuse `useRestTimer`, or they write into the real timer's
  slot.

## Known gaps

1. **No automated tests.** The best targets are `Formulas`, `StatsService`, `Outliers` and the CSV
   parsing (all pure), then the auth and ownership boundaries. `DemoData` makes a usable fixture.
2. **Rate-limit state is in-process**, so a second instance would double every budget.
3. **`MaxAccounts` is approximate**: concurrent registrations can both pass the check.
4. **`App__TrustProxyHeaders=true` is only safe behind the platform's proxy.** With the port exposed,
   anyone can forge `X-Forwarded-For` for a fresh rate-limit budget.
5. **Static files are not rate-limited**; this leans on the platform's limits.
6. **History shows the latest 20 workouts** (owner decision); older ones are reached through the
   month calendar.
7. **English only.**

## Deliberately not built

- **Offline/PWA.** A workout in progress needs no signal until Finish, but the app has to load and
  everything else is fetched live. The biggest UX upgrade left, and the biggest job.
- **Account recovery.** A lost code is a lost account, and the app says so.
- **A records table.** Replaying history is simpler to keep correct at this scale.
- **Social features.**

## Working on it

`dotnet run -- seed-demo` (Development only) creates an account with ~20 weeks of training,
including one deliberately stalled lift, and prints its login code.

Before committing:

```bash
dotnet build                                    # expect 0 warnings
cd src/web && npx tsc --noEmit -p tsconfig.app.json && npx oxlint src
```

**Schema changes:** `dotnet ef migrations add <Name> -o Data/Migrations`. On Windows a running
`dotnet run` locks the build output, so stop it first.

**Verifying changes** is done with throwaway Playwright scripts against the dev servers. Most bugs
so far were found by looking at the running app, not by reading code. Login allows 8 attempts per
15 minutes and registration 3 per hour per IP (in-process, so an API restart resets both). So sign
in once with a direct request to `:5199` and give the `rt_session` cookie to the browser. Test
destructive changes on a throwaway account, and delete it after with `DELETE /api/auth/me`.

**Local demo account:** login code `2395 9877 7198 1929 7123`. It's local only and worthless
elsewhere. A reseed mints a new code; update it here.
